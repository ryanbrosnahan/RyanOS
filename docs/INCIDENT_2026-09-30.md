# Repeated guard trips during adherence-report deployment

All times below are America/Chicago on September 30, 2026.

## Evidence

- The report release is `07c4ef4ee4f2e1d27d4940a3e55ab5afc7021cee`.
  It passed 166 tests, type checks, a local Linux image build, and a PDF test
  inside that image before transfer to Lenovo.
- At 22:39:53, D-Bus recorded 336 pending-reply-limit messages for
  NetworkManager. The guard paused Docker at 22:40:05. Guard evidence recorded
  zero veth events, bridge joins, or BuildKit failures in that window.
- A detached, operator-approved recovery restarted NetworkManager at 22:57:28,
  observed healthy networking, resumed Docker at 22:58:28, and passed local and
  external application health checks. All four containers remained running.
- The operator rearmed the guard at 23:01:32. It tripped again at 23:01:34 with
  30 saturation messages for the new NetworkManager process, again without
  Docker network churn. Docker was left paused.
- A privileged, header-only D-Bus capture at 23:03:49 showed a burst of
  `GetPermissions` calls from connection `:1.62` to NetworkManager, followed by
  many outgoing `CheckAuthorization` calls to PolicyKit. `busctl` mapped
  `:1.62` to Cinnamon PID 1736. The separate `nm-applet` process issued one
  permission request in the visible burst. Restarting NetworkManager had left
  the flooding desktop process intact.

The trace identifies the desktop caller. It does not establish a specific
upstream memory leak or prove that a particular newer package fixes it.

## Targeted mitigation

At approximately 23:07, the single `network@cinnamon.org` panel widget was
disabled and Cinnamon was restarted using its built-in X11 restart method.
Other panel entries were preserved. The prior setting is saved on Lenovo at:

```
/home/ryan/.config/ryanos-recovery/cinnamon-applets-20261001T040701Z.json
```

The new Cinnamon D-Bus connection is `:1.8432`. Docker stays paused until clean
network observations pass. The guard thresholds and D-Bus limits are unchanged.
Do not restore the widget without checking for recurrence. The separate
`nm-applet` remains available.

## Deployment recovery

The image import completed when Docker resumed, even though its client had
been cancelled during the pause. Verify these identities before resuming:

```
release: 07c4ef4ee4f2e1d27d4940a3e55ab5afc7021cee
image: sha256:c1499bb3b5938aabe3e2dcc2656ce34f460cc0302b38fec535609fda1f2e8b63
rollback tag: ryanos-app:rollback-20261001T033957Z
rollback image: sha256:1b7553f0ef49e380271df73f6ecc72459db78a67e9a9eae322e6f0f7c0451726
```

`scripts/deploy-lenovo.sh` supports resuming this already built and tested
release using `RYANOS_DEPLOY_RESUME_SHA`, `RYANOS_DEPLOY_RESUME_IMAGE_ID`, and
`RYANOS_DEPLOY_RESUME_ROLLBACK_TAG`. It requires matching, clean remote source,
the exact loaded image, and a rollback image matching the currently running
API. It retains the original release identity, makes a fresh database/key
backup, and performs the normal migration and health checks. It skips the
already completed build/import and Android publication.

Docker clients now have time limits and are cancelled when a new trip marker
appears. Deployment never clears a marker or changes Docker's pause state.
